# 荣泰智能 App（RT7709S）逆向分析报告

> 目标：搞清楚「荣泰智能」App 到底怎样控制按摩椅，并找到一条可以自己编排按摩程序的路。
> 结论先说：**你这台 RT7709S 是 Wi-Fi 机型，控制指令不走蓝牙，而是发到荣泰的云平台**。
> 我们把这条云端接口逆出来了，并且已经在你家椅子上实测跑通——现在可以用脚本按秒级时间线
> 任意编排官方 App 没有的按摩程序（见 `cli/`）。

- 手机：Xiaomi 17 Pro（Android 17），USB 调试已开启
- App：`com.rotai.intelligence`，版本 **2.5.2**（versionCode 135），targetSdk 30
- 按摩椅：**RT7709S**，MAC `AABBCCDDEEFF`，机型代码 `0626`
- 固件：controller 18.28 / main 1.15 / userInterface 5.19 / controllerConfig 0.00
- 分析时间：2026-10-28

---

## 1. 为什么官方 App 里「模式」不够用

App 里 RT7709S 能选的东西其实是写死的配置表（`assets/config/RT7709S.json`，83 条）：

- **12 个自动程序**：椅上瑜伽、脑力唤醒、放松冥想、总裁尊享、女王尊享、乐龄尊享、
  颈肩舒缓、脊背呵护、腰臀运动、清晨活力、午间小憩、良宵甜梦
- **手动设置**：手法、力度、速度、部位、时长、加热、气囊、零重力、姿态
- **我的程序**：本质是商城买的「烧录程序」（`PurchasedProgramBean`），而烧录程序走的是
  蓝牙写片内程序的通道，**RT7709S 是 Wi-Fi 机型，用不了这条通道**

也就是说：官方只能「选一个程序」或「调几个参数」，**不能把 A 程序的手法 + B 程序的力度 +
C 部位的节奏拼成一条自己的时间线**。这正是我们要补的那块。

## 2. App 的两条控制链路（关键发现）

APK 里同时实现了两套完全不同的设备协议（`com.rotai.module.device.base.ProtocolType`）：

| ProtocolType | 传输 | 适用机型（举例） | 实现类 |
|---|---|---|---|
| `STANDARD` / `LONG` / `NORMAL` | **BLE 蓝牙** | A60、RT7709Pro、RT8900 等 | `StandardChair` → `StandardBleSender` |
| `IOT` | **HTTP → 荣泰云** | **RT7709S**、RT7709、T8、YN8070 | `NetChair` → `NormalNetSender` |

决定性证据：`java/src3/com/rotai/module/device/net/RT7709S.java`

```java
public final class RT7709S extends NetChair {
   this.setConnectType(ConnectType.WIFI);
   this.setProtocolType(ProtocolType.IOT);
   this.setConfigType(WifiConfigType.AP);
}
```

而 `NetChair.initIoTDevice(mac)` 里装配的是：

```java
this.setSender(new NormalNetSender(mac));
this.setReceiver(new NormalNetOrderReceiver(mac, new NormalNetOrderConsumer()));
```

所以 App 里那个「蓝牙连接成功」的观感是假象：RT7709S 实际是 **Wi-Fi 模组 + 云端下发**。
（手机蓝牙里那条 `RT7709S` 记录只是配网/搜索时留下的 LE 广播缓存。）

### 2.1 云端接口（真正的控制面）

`java/src3/com/rotai/lib_net/api/NetApi.java`：

```java
private static String BASE_URL = "https://iot3.xingzhuo.xyz/";
```

`java/src3/com/rotai/lib_net/api/IoTApiService.java`：

```java
@POST("/api/bodydata/v1/iot")
Observable<WanResponse<SendCmdBean>> setDeviceProperty(@Header("token") String token,
                                                       @Body RequestBody body);

@POST("/api/bodydata/v1/iot")
Observable<WanResponse<DeviceStatusBean>> getDeviceProperties(@Header("token") String token,
                                                              @Body RequestBody body);

@GET("api/bodydata/v1/device/status")
Observable<WanResponse<DeviceOnlineBean>> checkDeviceIsOnline(@Header("token") String token,
                                                              @Query("mac") String mac);
```

`NormalNetSender.sendCommand()` 拼的请求体：

```json
{
  "mac": "AABBCCDDEEFF",
  "action": "SetDeviceProperty",
  "params": { "Items": { "SettingMassageSkill": 5 } }
}
```

`NormalNetOrderReceiver` 轮询状态（约 500ms 一次）用的是同一接口、不同 action：

```json
{ "mac": "AABBCCDDEEFF", "action": "QueryDevicePropertyStatus" }
```

响应统一信封：

```json
{ "code": 0, "message": "ok", "data": { ... } }
```

`code != 0` 即失败；`QueryDevicePropertyStatus` 的 `data.statusInfo` 是一个
`[{Identifier, Value, DataType, Name, Time, Unit}]` 数组。

**每次请求只带一个 `token` 头**，没有签名、没有时间戳（这一点已实测：从电脑上直接用
curl 就能控制，见第 5 节）。

### 2.2 蓝牙链路（顺带逆出来，供其它机型参考）

虽然 RT7709S 用不上，但既然拆了就记下来（`StandardOrderProducer` / `StandardBleSender`）：

- Service：`0000fff0-0000-1000-8000-00805f9b34fb`
- Notify：`0734594a-a8e7-4b1a-a6b1-cd5243059a57`；Write：动态取 `properties & 0x08` 的特征
- 帧格式（`55 AA` 开头）：

```
55 AA | dst | src(03) | seq | cmdHi | cmdLo | lenLo | lenHi | payload... | crcLo | crcHi
```

- `seq` 由发送器自增（`sendData()` 里 `data.set(4, wrIndexNum++)`）
- CRC：**CRC-16/CCITT-FALSE**（poly 0x1021，init 0xFFFF，无最终异或），低字节在前
- 空闲时每 250ms 发心跳 `55 AA 01 03 seq 01 20 00 00 crc`（命令 0x2001，长度 0）
- 命令字表在 `assets/command/Standard.json`（438 条）、`Long.json`、`Normal.json` 等
- 写程序用 `CMD_WRITE_PRO = {0x02,0x42}`、试运行 `CMD_TRY_PRO = {0x02,0x43}`
  （`ChairConstant.java`）——这就是商城「烧录程序」的底层通道

> 注意：字节序在代码里是 `cmd[1]`、`cmd[0]` 这样取的，写在一起容易看错；如果要真做蓝牙
> 客户端，建议先用 nRF Connect 手工发一帧验证 `payload` 的字节序再批量实现。

## 3. token 与 MAC 是怎么拿到的

App 把登录态放在 SharedPreferences，按摩椅列表放在 Room 数据库里。二者都可以通过
`allowBackup=true`（AndroidManifest 里没关）的 `adb backup` 拉出来：

- `sp/com.rotai.intelligence.xml` → `<string name="user_tokenrelease">…</string>`
- `db/room_intelligence.db` → 表 `connected_device` → `mac / title / type / protocolType`

实测备份包约 0.9 MB，解析后：

```
token : <YOUR_TOKEN>
mac   : AABBCCDDEEFF
title : RT7709S   type: WIFI   protocolType: IOT
```

`rtchair.py setup` 会自动完成整个流程（备份 → 解 tar → 取 token/MAC → 连通性自检），
已在本机实测通过（输出「✔ 云端连通，当前共 39 个状态项」）。要注意 Room 数据库的数据写在
`-wal` 文件里，必须把 `.db/-wal/-shm` 一起解出来再打开，否则 `connected_device` 表是空的。
备份时手机会弹「完全备份 / 备份我的数据」，点确认即可（不要设密码）。

补充：如果 token 失效，备选是走 App 自己的登录接口
（`POST https://iot3.xingzhuo.xyz/api/bodydata/v1/validate/send_phone_code` 发短信，
再 `POST /api/bodydata/v1/user/login`，表单字段 `phone` + `captcha`），
这条没在这次实测里用到，作为后备方案记在这里。

## 6. 局限性 / 风险

1. **强依赖云端**：椅子必须联网且荣泰 IoT 云在线；断网/服务下线就用不了。这次没有找到
   局域网直连或 MQTT 直连的入口（模组只和云通信）。
2. **token 会过期**：过期后重跑 `python3 rtchair.py setup`，或用 App 重新登录后重取。
   token 是账号级凭据，`~/.config/rtchair/config.json` 已设成 600 权限，别提交到公开仓库。
3. **不是官方接口**：固件/服务端字段可能被改动；属性值越界时椅子一般直接忽略，不会报错，
   但别乱试大数值。
4. **安全**：自动程序可以在无人看管时启动，请在自己在场时使用；老人/孕妇/骨质疏松等人群
   按说明书使用；不要用脚本做连续长时间运行。
5. **保修**：这里只做「云端下发 + 时间线编排」，不改固件、不写片内程序，风险很低；
   但仍属于非官方用法，自行判断。

## 7. 复现步骤（别人想复刻时）

```bash
# 1. 从手机拉 APK
adb pull /data/app/~~<hash>/com.rotai.intelligence-<hash>/base.apk
sha256sum base.apk   # a540dae7e3715f43d6e3e9eea5052cbe32d290c88b7d097450afa024bf297bcc

# 2. 解包资产
unzip base.apk -d apk_x   # assets/config/RT7709S.json、assets/command/Standard.json

# 3. dex → jar → java（本机用的 dex2jar 2.4 + Android Studio 自带 fernflower）
d2j-dex2jar.sh -f -o classes3.jar classes3.dex
java -cp java-decompiler.jar org.jetbrains.java.decompiler.main.decompiler.ConsoleDecompiler \
     classes3.jar out/

# 4. 找控制面
grep -rn "SetDeviceProperty\|iot3.xingzhuo" out/
```

> 分析环境里 jadx 发行包下载太慢，所以用了 dex2jar + fernflower；产物在 `java/src2`、`java/src3`，
> 中间件在 `jars/`、`disasm/`。功能上足够定位协议，Kotlin 协程相关代码反编译后略啰嗦。

## 8. 离线模式（已打通）

后续在路由器（ImmortalWrt）上抓到了完整云端协议：椅子连的是**阿里云 IoT MQTT
（1883 明文）**，控制指令就是往
`/sys/<pk>/<dn>/thing/service/property/set` 发一条 JSON：

```json
{"method":"thing.service.property.set","id":"<数字>",
 "params":{"ChairSwitch":1},"version":"1.0.0"}
```

据此实现了**完全离线**方案：路由器上跑一个极简 MQTT broker 冒充阿里云，
配一条持久化 DNAT 把椅子的 1883 流量劫持到本地 broker，电脑上的 `rtchair`
切到 `local` 模式即可控制。已在真椅子实测（开机/程序/手法/加热/时长全部生效）。

- 使用说明：`docs/离线模式-使用说明.md`
- 固件/刷机评估：`docs/固件与刷机评估.md`（结论：不建议刷机）
- OTA 只读侦察：`tools/ota_watch.py`
- 一键开启/关闭：`tools/offline_on.sh` / `tools/offline_off.sh`
- **Home Assistant 集成**：`custom_components/rtchair/`（28 个实体 + 自带仪表盘），
  一键部署 `tools/ha_deploy.sh`（含仪表盘），说明见 `docs/HA集成-使用说明.md`
