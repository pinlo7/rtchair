# 脱离云端控制 RT7709S —— 进展与落地方案

> 一句话现状：**离线「读」已经打通**（不联网就能实时拿到按摩椅 MCU 的全部状态帧）；
> **离线「写」还差最后一步**——需要抓一次云端下发给椅子的指令帧，把命令编码对上。
> 本文记录已确认的事实、已排除的猜测、以及最快打通的三条路。

## 0. 重大更新（2026-10-28 抓包后）

第一次抓包（脚本 v1，双向 ARP 欺骗）虽然把椅子的云端连接掐断了，但抓到了关键信息：

```
椅子 192.168.1.100  <->  47.100.25.136:1883   （明文 MQTT，无 TLS）
topic: /sys/<PRODUCT_KEY>/<DEVICE_NAME>/rrpc/request/<msgId>
payload: {"id":"123","version":"1.0","time":1793173871964}   ← 云端心跳(RRPC)
上行:   c0 00 (PINGREQ) ...
```

也就是说：**椅子连的是阿里云 IoT 平台（MQTT 1883 明文），不是私有 TCP 协议**。
这改变了解法——不需要逆 MCU 帧了，改用更干净的方案：

### 新方案：本地伪装阿里云 IoT（推荐）

模组把「云端下发的 JSON」翻译成 MCU 帧。那么只要：

1. 抓住云端下发的一条**控制消息**（比如开机），拿到它的 topic 和 payload JSON
2. 在本机跑一个极简 MQTT broker，冒充阿里云
3. 让椅子连到本机（DNS/ARP 把 `47.100.25.136` 或域名指过来）
4. broker 对模组的 CONNECT 直接回 CONNACK 成功，然后按捕获到的 topic/payload
   发布控制消息 —— 模组照样会翻译成 MCU 帧执行

这样连 MCU 协议都不用碰，纯局域网、纯 MQTT，最优雅。

> 第一次抓包只抓到心跳，是因为脚本 v1 把连接弄断了，手机按不动。
> 脚本 v2（`--manual` 或自动触发云端指令）只做**单向 ARP**，不会断网。

### 抓包 v1 的事故与恢复

- 现象：手机 App / 椅子面板都报网络错误
- 原因：v1 同时欺骗了椅子和网关，NAT 回程断了，椅子的 MQTT 连接被重置
- 恢复：一般 1~3 分钟 ARP 缓存过期后自动恢复；椅子现在云端状态已是 online。
  若面板仍旧报错，把椅子主电源关掉再开一次即可
- v1 还在 PC 上把 `net.ipv4.ip_forward` 留成了 1，无副作用；
  想归零：`sudo sysctl -w net.ipv4.ip_forward=0`


## 1. 已确认：椅子有一个局域网直连通道

RT7709S 的 Wi-Fi 模组是 **汉枫 HF-LPB130**（Hiflying），它同时干两件事：

1. 作为 TCP 客户端连到荣泰云（App 的控制指令就是这么来的）
2. 作为 **TCP 服务端**在局域网 `192.168.1.100:8899` 开一个透传口，
   把按摩椅主控（MCU）的串口数据原样吐出来

实测证据：

```
# UDP 48899 模块识别（汉枫专有发现协议）
send "HF-A11ASSISTHREAD" -> "192.168.1.100,AABBCCDDEEFF,HF-LPB130"

# 连 8899 立刻开始收到 MCU 上行帧（每帧 CRC 都校验通过）
55aa 0e 01 00 05 02 20 00 03000000...  crc
```

- 模组 MAC `AA:BB:CC:DD:EE:FF`，局域网 IP `192.168.1.100`，端口 `8899`
- 另有 `80` 端口 HTTPD（汉枫配置页，默认 `admin/admin` 能过认证，但页面全 404，
  且时开时关，靠不住）
- 三个地址含义：**MCU = 0x01，Wi-Fi 模组 = 0x0E，BLE 模组（老机型）= 0x03**

### 帧格式（逐帧 CRC 验证通过）

```
55 AA | dst | src | seq | cmdLo cmdHi | lenLo lenHi | payload … | crcLo crcHi
```

- `cmd`、`len`、`crc` 都是小端
- CRC = **CRC-16/CCITT-FALSE**（poly 0x1021，init 0xFFFF，无最终异或）
- 上行（MCU→模组）常见命令：

| cmd | 长度 | 含义 |
|---|---|---|
| `0x0202` | 64 | 配置块 |
| `0x0204` | 0 | 心跳 |
| `0x0205` | 32 | 状态遥测（一直刷，约 5Hz） |
| `0x0209` | 0 | 事件 |
| `0x0247` | 32 | 偏好块 |

### 已实现：离线状态读取

```bash
cd cli
python3 rtchair_local.py scan       # 按 MAC 找椅子 IP，记住
python3 rtchair_local.py monitor    # 实时看所有 MCU 帧
python3 rtchair_local.py snapshot -s 5 --json
```

不碰云、不需要 token、不需要账号，椅子只要通电在同一 Wi-Fi 就行。

## 2. 关键卡点：写命令的编码还没对上

我们往 `8899` 发帧，MCU **能收到**——而且是逐帧校验过的：

- 发**合法 CRC**、`dst=0x01` 的帧 → 立刻收到 MCU 的传输层 ACK
  `55 AA 0E 01 <seq> <cmd> 00 00 <crc>`
- 发 CRC 错误的帧 / 错的帧头 / 半截帧 → **完全没有应答**
- 发 `dst=0x0E` 的帧 → 没有应答

所以链路和寻址是对的，**是命令字/负载格式不对**。已经试过并排除的：

| 尝试 | 结果 |
|---|---|
| BLE 协议：帧 cmd=`0x2001` + `Standard.json` 命令码（如 `0001`、`2005`），两种字节序 | 无动作 |
| RT7709S 配置里的 `directive` 码（`1020`、`2012`、`4073`…）当 payload | 无动作 |
| `directive` 直接当帧 command（`0x1020` 空负载等） | 无动作 |
| `0x0201`/`0x0203`/`0x0205` 等 0x02xx 家族 + 各种短负载 | 无动作 |
| 「状态同步」：把 0x0205 的 32 字节状态块改位后发回 | 无动作 |
| 换 `src`（0x03/0x00/0x02/0x0E）、换 `seq` | 只影响 ACK，无动作 |

> 结论：这个 MCU 的「设置类」命令字/负载格式和 App 里 BLE 那套不一样，
> 盲猜成本太高。**最快的办法是抓一次云端下发的原始帧。**

## 3. 三条打通离线控制的路（按推荐顺序）

### 方案 A（最推荐）：抓一次「云 → 模组」的明文帧

椅子连荣泰云走的是 TCP 明文透传（HF-LPB130 不支持 TLS 透传），
所以只要在局域网上把椅子的出网流量镜像一次，就能看到云端下发的指令帧。

**前提**：电脑和椅子在同一个 Wi-Fi/局域网；电脑能用 `sudo`。

```bash
# 1) 装抓包工具（只用一次）
sudo apt install -y tcpdump dsniff

# 2) 运行抓包脚本（会自动 ARP 欺骗 + 转发 + 抓包）
sudo ./tools/capture_chair_cloud.sh

# 3) 按提示在手机上操作：开机 → 选程序 → 换手法 → 开加热 → 关机
#    每个动作停 2 秒，然后 Ctrl+C

# 4) 产物
/tmp/chair_cloud.pcap
```

拿到 pcap 后，直接跑现成的分析器（会自动分开上/下行、拆 55AA 帧、把只出现
一两次的「下发行命令」标出来）：

```bash
python3 tools/analyze_capture.py /tmp/chair_cloud.pcap --chair-ip 192.168.1.100
```

输出里 `方向 椅子IP -> 对端` 是 MCU 上报/ACK，`方向 云端 -> 椅子` 就是云端下发的
控制帧，`★` 标记的是低频帧——那就是「开机 / 换手法 / 开加热」对应的命令。
然后：

- `rtchair_local.py send --frame <hex>` 逐条验证
- 验证通过后，把 `rtchair.py` 的发送层从「HTTP 云端」换成「本地 8899 帧」，
  `programs/*.plan` 一个字都不用改，**彻底离线**
- 还可以顺手写一个**本地小服务**冒充云端（把模组的服务器地址指到 NAS/PC），
  这样官方 App 也能在纯内网里用

> 如果不想用 ARP 欺骗，等效做法：在路由器上把 DNS 里荣泰云的域名指到你的
> NAS/PC，跑一个透明 TCP 代理（记录 + 转发）也一样能拿到这些帧。
> 路由器后台（192.168.1.1）一般都有 DNS/hosts 设置。

### 方案 B：逆 MCU 固件

App 有固件升级功能，固件从荣泰 OSS 下载。拿到 RT7709S 主控/控制器的
bin（`controller 18.28` / `main 1.15`）后用 Ghidra 反汇编，直接找 55AA 帧的
命令分发函数，就能得到完整命令表。缺点：要先从云端 firmware 接口把 bin 挖出来
（接口参数还没凑齐），再逆一个 MCU 固件，工作量比 A 大一个量级。

### 方案 C：硬件直连

拆开椅子，在 Wi-Fi 模组和主控之间的 UART 上并一个 USB-TTL / ESP32，
自己当「模组」发帧。好处是不受模组固件限制；坏处是**命令格式仍然要方案 A 或 B
来解决**，而且涉及拆机、失去保修。适合把方案 A 的成果固化成一个常驻网关。

## 4. 现在就能用的离线能力

| 能力 | 状态 | 命令 |
|---|---|---|
| 局域网发现椅子 | ✅ | `python3 rtchair_local.py scan` |
| 离线读取 MCU 实时帧 | ✅ | `python3 rtchair_local.py monitor` |
| 离线抓帧存证/分析 | ✅ | `python3 rtchair_local.py snapshot --json` |
| 向 MCU 发任意帧（实验） | ✅ | `python3 rtchair_local.py send --cmd 0x2001 --payload 0001` |
| 离线**控制**（开机/手法/程序） | ⛔ 差命令编码 | 等方案 A 的 pcap |

## 5. 风险提示

- 抓包会让椅子短暂「掉线」（ARP 欺骗期间），操作完脚本会自动恢复
- 不要在抓包时同时跑云端控制脚本，日志会混在一起
- 别用未知的 `cmd` 长时间扫，MCU 可能有测试命令；一次只发一帧、看反应
- 模组换 IP 后重新 `rtchair_local.py scan` 即可
